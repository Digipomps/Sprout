# RELEASE

Current integration evidence and limits: [2026-09-18 validation](docs/Production_Integration_2026-09-18.md).

Updated: 2026-09-18. Terminal setup remains separate from verified Entity admission,
channel authorization and a signed production distribution.

## Artifact trust policy
- Require publisher signatures AND artifact hashes matching the signed
  `SHA256SUMS*.b64url` file for the actual target platform. Hashes alone cannot
  establish publisher identity.
- The default trusted Sigstore identity is the exact Digipomps/Sprout
  `release.yml` workflow on a version tag, with GitHub Actions' OIDC issuer.
  A valid signature from an arbitrary GitHub repository/workflow is not trusted.
- Trust only artifacts covered by the published release manifest and matching the expected runtime/version/channel.
- Update/install authority is separate from bootstrap. `sprout` does not self-update.
- CLI install/update is allowed only when `UpdateGrantPolicy` grants artifact name + hash + semver + channel + trigger identity/contract.

## Build the release bundle
macOS builds require the exact public CellProtocol checkout recorded in
`ci/cellprotocol-nearby-revision.txt`. CI checks it out under
`.release-dependencies/CellProtocol`; local builds may set
`SPROUT_CELLPROTOCOL_CHECKOUT` to an existing clean checkout at that revision.
The build never silently downloads or substitutes this source.

Default local bundle:
```bash
swift test
bash Scripts/build_release_bundle.sh dist
```

Native macOS platform-suffixed bundle:
```bash
swift test
bash Scripts/build_release_bundle.sh dist "macos-$(uname -m)"
```

Linux delivery uses the official static Linux SDK and matching open-source Swift
6.2.4 compiler. Installing Swift is a developer/build step, not a recipient step.
The Linux CI workflow installs the pinned SDK and executes the resulting artifact
after building it. Local reproduction:

```bash
swift sdk install https://download.swift.org/swift-6.2.4-release/static-sdk/swift-6.2.4-RELEASE/swift-6.2.4-RELEASE_static-linux-0.1.0.artifactbundle.tar.gz \
  --checksum 24bdf84495dd31a6de2eb679647c1982b747bfbfe1a2060c779d84dcecd902a4
SPROUT_STATIC_LINUX_SDK=x86_64-swift-linux-musl \
  bash Scripts/build_release_bundle.sh dist linux-x86_64
```

On macOS use the matching open-source compiler, NOT Xcode's compiler. Optional
build variables: `SPROUT_SWIFT_BIN`, `SPROUT_SWIFT_SDKS_PATH`,
`SPROUT_SCRATCH_PATH`, `SPROUT_BUILD_JOBS` (default 4). Sandbox disabling requires
explicit `SPROUT_DISABLE_SANDBOX=1`; it is not a recipient workaround. Package
resolution is frozen to Package.resolved during release builds.

Linux packaging uses `llvm-objcopy` from the selected compiler directory, or
`llvm-objcopy`/`objcopy` on PATH, to remove debug information from delivery copies.
Set `SPROUT_OBJCOPY_BIN` for an explicit tool. Full debug information remains in
the build directory. The packaged copies are platform-checked again, hashed,
and run in Linux CI after this transformation. Module caches stay outside dist.

The build checks actual Mach-O/ELF architecture before copying artifacts. Linux
artifacts must have neither PT_INTERP nor dynamic DT_NEEDED dependencies. Naming
a native macOS binary `sprout-linux-x86_64` no longer passes. Cross-compilation
is not a runtime test; a macOS host cannot execute the Linux result.

Artifacts produced:
- default local bundle:
  - `dist/sprout`
  - `dist/sprout-updater`
  - `dist/release-manifest.json`
  - `dist/SHA256SUMS.b64url`
  - `dist/sprout.spdx.json`
- platform-suffixed bundle example:
  - `dist/sprout-linux-x86_64`
  - `dist/sprout-updater-linux-x86_64`
  - `dist/release-manifest-linux-x86_64.json`
  - `dist/SHA256SUMS-linux-x86_64.b64url`
  - `dist/sprout-linux-x86_64.spdx.json`
- signatures/certificates are not produced by building; release signing below is
  required for delivery, for every listed artifact and the checksum file

macOS bundles also contain `haven-nearby[-macos-ARCH]` and
`nearby-source[-macos-ARCH].json`, both covered by the signed checksums. Install
the verified companion beside the installed `sprout` executable under the name
`haven-nearby`. `Scripts/test_packaged_nearby.py` runs the real packaged helper
and validates synthetic offers locally; it performs no browse or advertise
action and does not prove two-device discovery or Entity linking.
Linux Nearby discovery remains explicitly unavailable.

Note:
- `sprout-macos` is built in CI on macOS, but it is not currently part of the release bundle generated by `Scripts/build_release_bundle.sh`.

## Verify the release bundle locally
Default bundle:
```bash
bash Scripts/verify_release_bundle.sh dist
```

Platform-suffixed bundle:
```bash
bash Scripts/verify_release_bundle.sh dist "" dist/SHA256SUMS-linux-x86_64.b64url
```

This verifies:
- artifact hashes against the selected `SHA256SUMS*.b64url`
- mandatory matching cosign `.sig` and `.pem` pairs and trusted publisher
- checksum signature before parsing entries; safe basenames, unique entries and
  regular non-symlink files; no traversal or partial-signature fallback
- all selected artifacts, without running a downloaded executable or requiring
  Swift on the recipient's machine; requires `openssl`, `cosign` and Bash

For a locally built unsigned development bundle ONLY:

```bash
SPROUT_ALLOW_UNSIGNED=1 bash Scripts/verify_release_bundle.sh dist
```

This is integrity-only development checking, not trusted delivery. Never instruct
a recipient to use it to bypass release verification. GPG files may be emitted
as supplementary evidence by CI; the verifier's publisher policy is Sigstore,
not an optional GPG signature. `COSIGN_CERT_IDENTITY` is an explicit exact-identity
override for verifying CI candidates; it must not be taken from an untrusted
download. The default policy rejects branch CI artifacts as user releases.

Publisher verification follows the official
[Sigstore verification contract](https://docs.sigstore.dev/cosign/verifying/verify/):
signature material plus expected certificate identity and issuer. This script
does not disable transparency-log, certificate or signature checks.

The old March 8 report verified hashes of suffixed files but did not prove their
actual platform. It must not be used as evidence that Linux executables ran.

Create keyless signatures:
```bash
bash Scripts/sign_release_bundle.sh dist
bash Scripts/sign_release_bundle.sh dist dist/SHA256SUMS-linux-x86_64.b64url
```

Direct updater checksum verification (does NOT replace publisher verification;
only run the updater after verifying that updater's own publisher):
```bash
./dist/sprout-updater verify-bundle \
  --artifact-path ./dist/sprout \
  --checksum-file ./dist/SHA256SUMS.b64url

./dist/sprout-updater verify-bundle \
  --artifact-path ./dist/sprout-linux-x86_64 \
  --checksum-file ./dist/SHA256SUMS-linux-x86_64.b64url
```

Policy-gated install planning:
```bash
./dist/sprout-updater plan \
  --policy TestVectors/update_grant_policy.example.json \
  --artifact-path ./dist/sprout-linux-x86_64 \
  --artifact-name sprout-linux-x86_64 \
  --version 1.0.0 \
  --channel stable \
  --trigger contract:update-admin
```

## CI release evidence
GitHub Actions is configured to produce:
- macOS CLI bundle artifacts for `sprout` and `sprout-updater`
- Linux CLI bundle artifacts for `sprout` and `sprout-updater`
- platform-suffixed release manifest, checksum file and SPDX SBOM
- cosign keyless signatures for listed artifacts and checksum file
- optional detached GPG signature for the checksum file when release secrets are configured
- optional GitHub build provenance / SBOM attestations when repo variable `SPROUT_ENABLE_GITHUB_ATTESTATIONS=true`
- native execution of the actual static Linux artifact's doctor and onboarding
  smoke before signing; these newly edited workflow steps have not run remotely
- an exact tag/source gate: manual dispatch must select the existing version tag
  AND specify that same tag as `release_tag`; branch-based releases are rejected

Current limitation:
- GitHub attestations are disabled by default because the private Digipomps repository plan does not currently support the attestation API
- Linux WSS transport parity is not part of the release baseline yet; Linux support is CLI/bootstrap/update/verification first
- `sprout-macos` is built in CI, but its separate release packaging/notarization path remains a later step
- the SBOM generator currently describes local Swift source targets, not a
  complete dependency/static-SDK/native-library inventory

## Reproducible build target
Target:
1. Build from immutable git tag in a clean environment.
2. Run `bash Scripts/build_release_bundle.sh dist <platform-suffix>`.
3. Compare `dist/SHA256SUMS-<platform-suffix>.b64url` against the published checksum file.
4. Verify checksum signature and provenance attestations.

Current status:
- local bundle generation and checksum verification are implemented for default and platform-suffixed bundles
- CI keyless signing is wired for non-PR runs on macOS and Linux
- GitHub attestations are opt-in and require repository support before they can be treated as release baseline
- bit-for-bit reproducibility across independent environments remains an explicit release goal, not yet proven in CI
- generated timestamps, SBOM UUIDs, toolchain identity and build paths still need
  deterministic treatment before whole-bundle bit-for-bit claims are justified
- signatures attest the selected publisher and bytes; they do not prove that
  source code is harmless or that a running process has never been modified

## Runtime-specific release policy
### CLI / server
- Preferred: operator-managed replacement of immutable signed artifacts.
- `sprout-updater` may plan or verify installs, but install mutation remains outside `sprout`.
- Supported native Linux baseline: Ubuntu 22.04 `x86_64` without Docker.
- The new portable candidate is fully static x86_64 Linux; runtime validation
  on that baseline and the recipient's environment remains a delivery gate.

### macOS
- Outside App Store, code signing and notarization are required before distribution.
- `sprout-macos` packaging is not part of the current release bundle script.
- Sparkle or any auto-update path is deferred until explicit grants + stronger metadata controls exist.

### iOS
- App Store only.
- No custom updater.
